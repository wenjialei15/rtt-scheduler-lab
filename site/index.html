四个数

同一台机器跑三次，取范围。绝对值只在这个模拟环境里成立。

实验测什么结果稳定性
E1 抢占高优先级能否打断低优先级LMHhml3/3 一致
E2 时间片同优先级两个线程的循环次数比1.12 / 1.18 / 1.21波动 ±20%
E4 邮箱两个线程 ping-pong 500 次45 / 49 / 55 µs±10%
E5 切换连续 rt_thread_yield() 5000 次4.89 / 4.95 / 5.32 µs±5%
5 µs 不是 Cortex-M 的真实切换时间——这里每次切换都要经过一次 Windows 的 SuspendThread / ResumeThread。这个数只能用来做同环境下的相对比较。

两个必须踩的坑

必须编 32 位

RT-Thread 的 rt_base_t 定义成 long。Windows 64 位是 LLP64，long 只有 32 位，直接编 64 位会把指针截断——堆初始化就崩。

主线程栈至少 8 KB

4 KB 时，第一个线程里调 rt_kprintf 就崩。裸机上够用的栈，到了桌面 CRT 的 vsnprintf 面前不够。

zig cc -target x86-windows-gnu \
  -Iport -Ithird_party/rt-thread/include \
  third_party/rt-thread/src/*.c \
  third_party/rt-thread/libcpu/sim/win32/cpu_port.c \
  port/board.c src/main.c -lwinmm -o build/rtt.exe

没能测出来的那一项

原本还有 E3：优先级继承——低优先级线程持锁时，中优先级线程能不能抢在它前面跑。

实测日志停在 L+ H? H+，L-、M+、M- 全部丢失。怀疑是移植层在改线程优先级时先 SuspendThread，恢复路径没有走回来。代码留在仓库里，注释掉了。

与其编一个「测出来了」的结论，不如把没测出来的原因写清楚。

边界

  • 模拟器不是真机：线程映射成 Windows 线程，切换走 SuspendThread，绝对数字不可外推。
  • E2 的 ±20% 波动来自宿主调度，不是 RT-Thread 的时间片算法。
  • 只编了 32 位；64 位要先把 rt_base_t 换成 64 位类型。
  • 没有跑文件系统、网络和 finsh，只保留内核与 IPC。
